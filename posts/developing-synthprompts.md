
# A look into a combinatorial pipeline for generating semirealistic synthetic user prompts

Synthprompts ([lyraaaa/synthprompts_v2_250k](https://huggingface.co/datasets/lyraaaa/synthprompts_v2_250k)) is a dataset of a few hundred thousand singleturn user prompts, designed to have a broad coverage of styles, lengths, topics, complexities, languages, etc. All category metadata is available so filtering for various experiments is trivial, and a random sampling is much more diverse than stock prompts, especially llm-generated ones. If you *have* real user prompts, you might want to use them, but there are many reasons you might want controlled synthetic ones, and even real prompts aren't necessarily diverse enough to capture the long tail of weird user behavior. 

![A screenshot of the huggingface data viewer showing some rows from synthprompts, with various combinations of topic, style, language, length, etc and the resulting prompts](posts/img/synthprompts-dataviewer.png)

---

# why

If you found your way to this post, you probably already know what a dataset of user prompts can be useful for. feature extraction, behavior audits, some kinds of RL, benchmarks, usersims, and so on. In a lot of projects, these come from stock lists of llm-written prompts, often built on the fly as an agent builds scaffolding, or pregenerated without much attention paid towards diversity and coverage.

Models typically have a rather charitable interpretation of what prompts are supposed to look like compared to the average human. They've seen prompting guides, example prompts, etc. Their prompts lean towards example-shaped well-formatted short prompts - ask a stock claude to write an activation extractor with prompts built in, and you'll see `def fibonacci(n):`, `Write a haiku about winter.`, and `What is the capital of France?` every time. 

It will attempt making categories - factual, reasoning, creative, etc. It knows coverage is important, but the actual prompts are flattened into the same set every time. Train going at 60mph, once upon a time, water boils at, and so on. The same ones often appear over and over, matched to the byte. You'll get some variance within the template, but the template never changes.

Nobody actually prompts like this. Yes, sometimes people ask short factual questions, but the venn diagram of "things real people ask for" and "test prompts generated by llm" is barely touching. 

Ok, so how do people actually prompt? We can look at [arena.ai data](https://huggingface.co/datasets/lmarena-ai/arena-human-preference-140k): they ask how their media expert job interview went and what the hiring rates are. Or espresso recipes for their specific philips lattego EP5547/90. Or a sheet-metal stamping force calculation with actual dimensions and a yield strength. "Desvribe kokushibo eyes from demon slayer". "And what if i am fearful avoidant?". "Hello, what is Rak". The prompts are noisy, hyperspecific, multilingual, and cover a *huge* variety of lengths, styles, and topics. Claude never writes this kind of stuff. It's too specific. 

Of course, arena isn't perfectly representative. It overrepresents testing and redteaming, since it is an evaluation site after all. They're supposed to be auditioning models, so they send them weird stuff. The logs the big labs have probably overrepresent agentic SWE tasks. Nothing has perfect coverage, every source is biased. So you don't necessarily want real prompts either. If you sample naive ai-gen prompts you get a lot of clean factual QA, write fibonacci in JS, and high school textbook logic problems. Sample unbiased real user prompts and you get a lot of agentic SWE, life advice, homework, web search, and small scale editorial stuff (ie reword this email).

What dies with poor selection is the long tail - niche use cases, the depths of hyperspecificity that comes with knowledge work, the pragmatics that comes with users underspecifying or overspecifying, the robustness that comes with ESL and odd requests. When a model feels benchmaxxed, often that's because it's overrepresenting a certain type of user - typically logic and SWE - and leaving the long tail to get clipped off by RL or distillation favoring only what helps with a certain subset of prompts. 

Controlled synthetic data is how you sample that long tail of OOD-ish user behavior with enough samples to make a dent. But... you need to avoid stylistically collapsing at the datagen phase.

# what

I've previously tried to do promptgen in a variety of ways for past projects. Sampling a model with `/completions` seeded only with `<|im_start|>user`, for instance. This worked, actually, but the resulting prompts were still somewhat mode collapsed and really hard to get good coverage. It might take 50 rerolls to get a SWE prompt, or you might never get some other style, etc. I wanted coverage good enough to run completions, cache their activations, and use them to train an SAE or similar. If I was missing a certain topic or style, it would get no associated features. 

So, how do you get synthetic prompts that:
- sound semi-realistic, 
- have broad coverage across some number of Important Things (style, topic, etc)
- end up actually being useful?

If I sample the model's user-turn token distribution, it's biased to the training data. If I sample lmarena prompts, it's biased to the evaluators and homework farmers. If I sample "what claude thinks a prompt is", it's biased to hello world test prompts. 

Well if all the issues with prompt data come from sampling biased distributions, why not impose my own distribution? Instruct models these days are pretty good at following constraints like that, so if I just wrote long lists of topics, styles, caveats, lengths, and so on, and randomly chose one entry from each list, I would get something like:

> gardening, 20-50 words, wanting feedback, already-tried-X, technical language

which even a smaller model can follow, and come up with something like this:

> "I'm trying to fix a nitrogen deficiency in my blueberries, but the soil pH is sitting at 6.2 and they're still chlorotic. I've already tried a top-dressing of elemental sulfur to lower the pH, but it's not moving. Any ideas on a more aggressive acidification strategy?"

Already it sounds much more like something an actual user would type into an LLM than something like "A train leaves Station A at 9 AM traveling at 60 mph. Station B is 120 miles away. What time does it arrive at?"

---

It's also interesting to consider that frontier models have some degree of eval awareness - they know when a prompt sounds like a test, and they change their behavior accordingly. Claude has [demonstrated eval awareness](https://www.anthropic.com/engineering/eval-awareness-browsecomp) [multiple times](https://www.apolloresearch.ai/science/claude-sonnet-37-often-knows-when-its-in-alignment-evaluations), GPT-5.6 often leans heavily into more reward hacking behavior when its prompts or environment resemble a training gym in ways it doesn't in obviously real situations, and I don't consider it that much of a stretch that the models on the open frontier (latest Kimi, latest GLM, etc) will develop or already have developed a similar skill. Even without explicit eval awareness, obviously test-shaped prompts fire different activations than real ones. If you want realistic behavior, even if the difference is minuscule, it's worth using realistic-looking prompts.

# how

*tl;dr I wrote a lot of lists, randomly combined items from them, pasted the selections into a sysprompt, sent the sysprompt to Gemma4 31B, and saved the resulting output.*

The key to making this whole combinatorial setup work is extensive category lists and careful blacklisting of categories that don't make sense together. 

The categories I chose for synthprompts were:

217 topics, 64 styles, 8 lengths, 16 languages, and some mode-specific ones like complexity (talk only) or spec level (task only).

Topics are entire domains, not specific prompts. "Plumbing" is a topic, "leaky faucet" is not. Models are good at inventing details, you just need to put it in approximately the right neighborhood. To keep things clean, there are multiple topic categories:

- Software engineering
- Household & practical
- Cooking & food
- Creative (task)
- Creative (talk)
- Science & academic
- Personal & life
- NSFW
- Casual conversation
- Meta/adversarial/model-directed
- Niche hobbies
- Technology & digital life
- Health & fitness
- Meta & philosophical
- Data/extraction/transformation tasks

Each of those have further subtopics that make up the actual topic items selected for the sysprompt. For example

```py
("version control and collaboration", "both"),
("cloud services and deployment", "both"),
("CLI and developer tooling", "both"),
("code architecture and design patterns", "talk"),
("open source and community", "talk"),
("technical writing and documentation", "both"),
("code review and debugging", "task"),
```

Styles, complexities, etc are written similarly:

```py
# styles
"rambly and tangential — goes off on sidetracks, parentheticals inside parentheticals, but eventually gets to the point",
"consulting-speak — frameworks, deliverables, polished to a mirror shine, management jargon as native language",
"misspelled and typo-heavy — genuine mistakes, autocorrect artifacts, typing fast and not proofreading",
"deadpan dry humor — flat delivery, understated, the joke is in what you don't say",
"quietly desperate — trying to sound calm but the urgency leaks through in small ways",
"deeply specific hyperfixation — knows WAY too much about this one thing, infodumps lovingly",
```

```py
# added complexity
"missing context — they haven't shared a key detail (they may not know it matters), and the right answer depends on it",
"time pressure — they need an answer fast and can't do the thorough/proper approach right now",
"already tried everything — they've been at this for hours, have tried the obvious things, need something non-obvious",
"legacy constraints — they can't use the modern/clean solution because of existing dependencies or decisions",
```

```py
# lengths
"a couple sentences — 15-40 words, enough to give context",
"a few paragraphs — 150-300 words, thorough setup with multiple aspects",
```

I tried to keep the topics broad and reflective-ish of actual humans' lives, so they likely overindex on home advice and away from, say, pokemon lore or agentic SWE. Improvements to the categories themselves would improve the entire pipeline a lot - the more exhaustive the combinations, the better coverage you get. 

It's also important to cover topics an LLM would not naturally touch - NSFW, for instance. For a lot of people, that is a primary use case, so it deserves a place in any dataset claiming to be diverse and representative. It can always be filtered at data-load time, but for things like activation collection, you need to have it available. 

I also chose to let the model handle cultural rendering - whatever "dad energy" means for a prompt in Hindi is left up to Gemma to decide. According to Claude (I can't read Hindi nor do I have the cultural knowledge to tell myself), they were mostly fine.

For styles I found it important to only describe the register and never give example words, since it would overindex on the example words and use them religiously - treating them as a checklist not a general vibe. The prompt writer is also not perfect at styles, for example it understands slang as the out-of-date kind, or stereotypes the voice when asked for stoner thoughts. Specification is also tricky - "4chan greentext" didn't survive translation, but "anonymous-imageboard story format" did. Adherence could be improved here.

I also chose to weight certain axes during selection to approximate a target distribution. For instance, I chose 55% talk and 45% tasks, even though tasks are more representative of real world use, because talk is easier for my system to generate and would lead to fewer rejections and rerolls during filtering. A talk-only dataset would probably be *better*, but less *realistic*. Language also got hit hard with the bias - I chose 60% english, 5% spanish, and 1-3% for the others. This was chosen entirely on vibes. 

### tasks and artifacts

Talk prompts are simple - a question, a problem, a conversation. Something easily written and easier to fake realism for. Task prompts are much harder - they operate on material. A prewritten paragraph, a chunk of data, some code, etc. The data in real use cases are often long, messy, and hyperspecific. 

Gemma really did not want to do this. It either dodged it ("[paste your code here]"), confidently referenced data that was never included ("analyze my sales numbers and tell me which region is underperforming"... what sales numbers lol), or just gave the laziest data possible. 

For singleturn prompts like these, the artifact has to be in the prompt, because there is no followup to paste it. Unless you want all the responses to these prompts to be "Sounds good, paste it when you're ready and I'll do [thing]", the artifacts need to be included. 

The temporary fix I used to get synthprompts_v2 out the door was adding a hard requirement for the artifact in the axis text itself. The spec levels had to literally say "prompt MUST include the source text", and even then a large percentage of them got filtered out for poor artifact quality and had to be rerolled. 

That did not solve the realism problem though - the artifacts are still the weakest-looking things in the entire dataset (except maybe the really short prompts), consistently short, underspecified, or obviously fake data. the csvs produced are too clean, the simulated email chain reads like an LLM talking to itself, and the code is toy examples.

To do it properly, I would probably need to create a version of this system specifically to generate fake artifacts, then use them as input to the synthprompts pipeline so gemma can focus on writing the prompt to go along with it. That would give more finegrained control over the style, detail, and quality of the artifact, avoiding the "gemma is lazy and writes hello-world tier CSV or leaves it blank completely" problems with the synthprompts_v2 pipeline.

### blacklisting

Some combinations don't get along. For example: `length: terse, ~10 words` and `style: long, rambly, storytelling` cannot coexist as described. So, a blacklist of certain pairings was used to exclude obviously nonsensical ones.

**Topics where structural complexity makes no sense:** casual small talk and banter, asking for entertainment or fun, casual interaction with AI (how are you, what do you like, etc), venting and emotional processing.

**Styles where multilingual prompts don't make sense:** ESL learner.

**Certain topic/complexity pairs made no sense:** casual small talk + already tried everything, asking for entertainment + already tried everything, casual small talk + overconstrained.

**Topics where spec makes no sense:** proofread and grammar check + [full spec doc, heavily specified, conflicting constraints]

Multiple styles conflict with multiple length constraints - too many to bother listing out here explicitly. See `axes_v2.py` in the dataset repo.

### generating

A seeded RNG chose combinations of topic, style, length, talk/task, complexities, etc from the lists, taking bias and blacklists into account. These were assembled into a large sysprompt (shown in full at the end of this post) asking Gemma4-31B on openrouter to write a prompt fulfilling those requirements. The calls were batched and streamed to jsonl as they returned. 

I chose to generate 250,000 prompts (out of many more possible) because nice round number that was within my side project budget. The total cost of the initial run of 250k prompts was ~$44, with an additional ~$20 spent on rerolls post-filtering. Judge calls cost ~half that.

### filtering

After generating 250,000 prompts, I ran certain suspect subsets of them (everything short enough to be potentially unanswerable, plus every task prompt with detected brackets etc) back through gemma as a judge, determining whether they fit the criteria requested. Any that did not pass gemma's smell test were removed (in hindsight, I had a rubric written that scored 1-7, and I should have passed anything 6+ rather than using a y/n grader), and more prompts generated until the list reached 250k again. That process was repeated until all 250k passed gemma's naive smell test. This is the final list that got shipped to huggingface.

I also ran a second judge pass on just the task prompts, checking whether the provided artifact was good, and asking the judge (yes, I know, bad design) to replace it if it wasn't at least usable. Many were cut and replaced this way, but many other poor quality artifacts made it through anyways. The entire artifact-generation system needs an overhaul, I'm still working on ideas for how to handle that in synthprompts_v3.

If I had more funds to run a more thorough eval, with multiple passes or better models, the selection would be a lot tighter. It is probably much better to grade each prompt against each axis individually instead of all at once, and then reject any where *any* category was a no-match.

# whats next

Early iterations of synthprompts have some glaring weaknesses and missing features still, hopefully to be improved in v3 and after. Many of the issues can be improved with a better generator model and more/better llm-as-judge filtering, which I skipped to keep costs low. There is still plenty of low hanging fruit with the current system.

Some weaknesses I know of right now:

**User artifacts.** Covered above - the weakest area by far. Generating realistic looking artifacts and data is harder than the prompts, and Gemma is lazy. Needs its own pipeline.

**Content control.** The axes do a good job of covering broad topics, but they don't select for content within them. Gemma chooses the actual content, and it has favorites. Keep rolling gardening prompts and you'll see the same monstera x neem oil questions reappearing frequently. It's potentially worth further subdividing topics so the mode collapse problem doesn't reappear within each category. 

**Multiturn.** Synthprompts is singleturn. This is partly by design, as very frequently followup prompts depend on the response to the original prompt, which is not known until inference time and can't be generated ahead of time. A system like the synthprompt generator could be wired up to an actual live system so the same user style settings could be used on the fly to write followups, perhaps with some extra axes like satisfaction etc.

**Adherence and spec length.** Synthprompts were oneshot by Gemma 4 31b, with a rather massive prompt. It struggled with adhering to the firehose of constraints and requirements frontloaded to it, and could be improved (with extra cost) by a multipass process. Rewriting, content-first-style-later, maybe drafting the prompt description first and then generating from that, etc. Even just using a larger, more capable, more expensive model would improve the outputs - I love gemma4, but it's still a small local model. Using something like GLM5.3 or a frontier model is worth trying, I skipped that for cost reasons.

**Flawed knowledge.** Often, Gemma will hallucinate a fact in a prompt (like, cinnabar moths eat ragwort, not aphids). It's not a dealbreaker, since user-being-wrong is something an LLM should be able to handle in-distribution. A good QC pipeline should be able to flag this, and you can decide whether or not you want your prompts subset to include incorrect user facts in whatever pipeline you're deploying the prompts in, thanks to tag filtering.

# extras

Some further work on filtering and improving synthprompts via llm-as-judge filtering: [kalomaze/glm52-usersim-two-pass-gemma-audit-v1](https://huggingface.co/datasets/kalomaze/glm52-usersim-two-pass-gemma-audit-v1)

Kalo sampled 10k prompts from my dataset and ran them through five quality checks, each judged 8 times by Gemma4-26B. 86% of them passed all 5 checks. GLM-5.2 wrote 8 answers for each prompt that passed, and after dedup, those answers each got their own quality checks, one more 8x5 audit and then one adversarial check on the ones that survived that. 45.7k answers passed the first check, 17.4k passed both. See repo for more details. 

Interestingly, the vast majority of prompt-quality failures found by kalo's Gemma filterer were weak "user artifacts" - the original document or data accompanying a task prompt. This is a known issue; realistic user artifacts are even more difficult to generate than realistic user prompts as described above. The remaining failures were mostly metadata adherence or missed blacklist combinations, improvable with a better model/better prompting.

### the initial prompt generation sysprompt:

```md
You are a prompt writer. You will receive a spec describing a topic, writing style, approximate length, and complexity type. Write one realistic user prompt — something a real person would actually type into a chat with an AI assistant.

## The #1 rule

Every prompt you write must be **answerable**. These are inputs to an AI assistant. The person is asking for help, information, advice, explanation, feedback, or a solution. Even if they're venting, even if they're rambling, even if they bury the question — there must be something an AI can substantively respond to. A prompt that's just a thank-you, just a statement with no implicit question, or just a performance piece with nothing to respond to is a failed prompt.

The style and length specs exist to ensure variety — they are constraints on **how** the person writes, not **what** they're writing. The what is always: a person who wants something from an AI assistant.

These are **first-turn prompts** — the opening message of a new conversation. There is no prior context, no previous exchange, no "as I mentioned earlier." The person is starting fresh. They should include whatever context is needed for the AI to respond, because nothing came before this message.

## What makes a good prompt

A good prompt sounds like it was written by a specific human being in a specific moment. Not a template. Not a writing exercise. A real person with a real problem or question or thing they want to talk about.

- The style specs are for variety, not rigid compliance. Use them to shape the voice and register, but never let style override substance. A prompt that perfectly nails the style but has nothing to answer is worthless. A prompt that's slightly off-style but asks a great question is fine.
- Match the length. The word count in the spec is for the prompt you write, not for the response the prompt is asking for. A "3-8 word" prompt is literally a few words. A "300-500 word" prompt is someone dumping a wall of context — but even a wall of context should end with something the AI can help with.
- Short prompts must still be on-topic. Even at 5 words, the topic should be identifiable from the prompt alone. "help me please" could be about anything — that's a failed prompt. "drain still gurgling help" is plumbing. "ts won't compile" is coding. The shorter the prompt, the more the topic-specific details matter because there's no room for generic filler.
- Invent specific situational details. The topic is the domain — you supply the specific scenario, the specific tools, the specific constraints, the specific mess they're in. Make it concrete and particular. A real person with a real situation, not a generic question about a category.
- Honor the complexity type. If the spec says "XY problem," the person should be asking about their attempted solution, and the real problem should be detectable underneath. If it says "has a gotcha," there should be a non-obvious catch that the person doesn't realize. If it says "straightforward," keep it clean and direct.
- Honor the mode. If the mode is "task," the prompt must be an imperative instruction — the user is telling the AI to produce, create, write, build, translate, fix, or deliver something. Not asking how. Not seeking advice. Telling. "Write me a poem about X." "Translate this." "Fix this code." "Draft a migration plan." The prompt can include context and background, but it must contain a direct instruction. If the mode is "talk," the prompt is discussion, advice-seeking, or thinking out loud — no imperative required.
- If the task spec level mentions "rewrite," the prompt must include actual source material to be rewritten — real text, real code, real content. Never use placeholder brackets like [paste here] or [insert text]. Invent the source material.
- Vary everything. Don't start every prompt the same way. Some people ask questions. Some people dump context and then ask. Some people just describe a situation and implicitly want help. Some people paste errors or code. Some people vent first then ask. Real prompts are structurally diverse — but they all want something.

## What to avoid

- Meta-language. Never write "Here is a prompt about..." — just write the prompt itself.
- Placeholder specifics. Never use generic nouns when you could invent a concrete one.
- Sanitized language. Real people express frustration, self-deprecation, excitement. Match the register of the style.
- Performing the style instead of being it. Don't narrate the style — inhabit it.

## Output format

Return ONLY the prompt text. No quotes, no markdown fences, no commentary, no metadata. Just the prompt exactly as a user would type it.
```

### the answerability judge prompt:

```md
You will receive a numbered list of user prompts. For each one, decide: could an AI
assistant give a useful, substantive answer to this prompt as-is? Or would it need to
ask clarifying questions first because there isn't enough context?

Rules:
- ANSWERABLE means a knowledgeable person could give a helpful response without
  guessing what the user means
- NEEDS_CONTEXT means the prompt is too vague, ambiguous, or missing critical details
  to answer usefully
- A prompt can be short and still answerable ("what is vo2 max" is fine)
- A prompt that names a topic but gives no specifics is NOT answerable
  ("all tuning fail what else")

Reply with ONLY a JSON object mapping each number to "A" or "N".
Example: {"1":"A","2":"N","3":"A"}
```

### the task/talk placeholder judge prompt:

```md
You are classifying whether user prompts are TASK or TALK.

TASK = the user tells the AI to DO something and deliver a result. "Write X",
"Translate Y", "Fix this", "Draft a plan", "Can you make..." are all tasks.
TALK = the user asks a question or seeks advice. "How do I...", "What is the best...",
"Any tips for..." are talk.

Also check: does the prompt use [placeholder brackets] where real content should be?

Think carefully about each one, then respond with ONLY a JSON object mapping each
number to one of: T (task), K (talk), TB (task+brackets), KB (talk+brackets)
Example: {"1":"T","2":"K","3":"TB"}
```
